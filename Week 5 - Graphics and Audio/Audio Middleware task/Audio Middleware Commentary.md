# Audio Middleware Commentary 

## How FMOD or Wwise was integrated
I integrated FMOD into the Unity project and linked it to my FMOD Studio project so that audio sits in its own proper system instead of getting messy across random gameplay scripts. I used FMODUnity and FMOD.Studio inside a central AudioManager asset to handle playback, instance tracking and cleanup, whilst keeping movement, collision and level scripts focused on what they are supposed to do. For quick one-off sounds, AudioManager calls RuntimeManager.PlayOneShot at a world position. For ongoing audio like the background music, it creates and tracks an FMOD.Studio.EventInstance so that parameters can be updated later and active instances get stopped and released cleanly on OnDestroy. Putting this logic in one place saved me from having to repeat audio code everywhere as well as avoiding stray references across scripts and keeping code much easier to maintain as I added new mechanics, checked collisions and tested the main gameplay.

## What event(s) were triggered and logged
On the gameplay side, the main events and logs were tied straight to testing player movement, audio triggers and scene setup during development. When the player is grounded in the player script, pressing space calls AudioManager.instance.PlayOneShot with jumpSound at the player's position, keeping jump audio tied to actual jumps rather than mid-air presses. For continuous audio, AudioManager.Start initialises a looping backgroundMusic EventReference as an EventInstance and starts it automatically as soon as the scene load, with a helper method ready if I want to update music parameters dynamically when gameplay state or area change. I also relied on logging to catch mistakes early instead of guessing why something was silent or not working. AudioManager logs an error if a second manager ends up in the scene. Also I added temporary debug logs while sorting out ground checks, collider overlaps and coin triggers so that I could actually see what was firing while tuning player variables.

## How you validated the middleware in a packaged build
Testing only inside the Unity Editor can easily miss bank, path or teardown issues so I also validated how the setup behaved in a packaged build. First I made sure the FMOD Studio project was built properly so all the banks and events we compiled into the build data rather than left not build or missing. Next I launched the packaged build and played the game to check that the background music started on its own without missing bank or any null reference errors and that jumping and collecting still triggered their FMOD events cleanly. Finally, I checked the build log output for FMOD or AudioManager warnings and made sure closing the application or leaving the scene stopped and released active EventInstance handles properly instead of leaving audio hanging around or leaking resources. Doing that standalone build check gave me a lot more confidence that the audio setup actually worked outside the editor and would hold up properly when sharing the build.
